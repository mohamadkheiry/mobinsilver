# عملیات، مانیتورینگ و پشتیبانی

## 1. هدف

این Runbook برای نگهداری روزمره، تشخیص خطا، مدیریت رخداد، بکاپ و پاسخ‌گویی به درخواست مشتری تهیه شده است. دسترسی به production باید مبتنی بر نقش، ثبت‌شده و حداقلی باشد.

## 2. مالکیت پیشنهادی

| حوزه | مالک اصلی | جایگزین |
|---|---|---|
| رابط و تجربه مشتری | Frontend Team | Product Owner |
| API و منطق سفارش | Backend Team | Tech Lead |
| پایگاه داده و بکاپ | DevOps/DBA | Backend Lead |
| پرداخت و تطبیق مالی | Finance + Backend | Operations Lead |
| امنیت | Security Owner | Tech Lead |
| پاسخ مشتری | Support | Operations |

نام و اطلاعات تماس واقعی باید در ابزار داخلی سازمان نگهداری شوند، نه repository عمومی.

## 3. شاخص‌ها و SLIهای پیشنهادی

- availability مسیر `/api/health`
- نرخ موفقیت login و register
- نرخ `POST /api/orders` موفق، 4xx و 5xx
- latency صدک 50، 95 و 99 API
- تعداد سفارش Pending بیش از آستانه زمانی
- تعداد محصولات Stock صفر یا زیر حد
- خطاهای payment verify و webhook آینده
- اختلاف مبلغ سفارش و پرداخت
- زمان از ثبت تا آماده‌سازی و ارسال
- خطاهای frontend و Core Web Vitals
- فضای دیسک، connection pool و سلامت دیتابیس

## 4. هشدارهای پیشنهادی

| هشدار | سطح | اقدام اولیه |
|---|---|---|
| health failure بیش از 2 دقیقه | Critical | بررسی process، reverse proxy و DB؛ آماده rollback |
| 5xx بیشتر از 2% در 5 دقیقه | High | بررسی release اخیر و traceها |
| ثبت سفارش صفر با ترافیک عادی | High | بررسی checkout، API و درگاه |
| Payment موفق بدون Order Paid | Critical | توقف پردازش مالی و reconciliation |
| فضای دیسک بالاتر از 85% | High | پاکسازی artifact/log طبق retention |
| backup ناموفق | Critical | اجرای مجدد و بررسی مقصد بکاپ |
| تلاش ورود Admin غیرعادی | High | محدودسازی، rotation و بررسی audit |

آستانه‌ها باید پس از جمع‌آوری baseline واقعی تنظیم شوند.

## 5. سطح‌بندی رخداد

- SEV-1: توقف کامل فروش، نشت داده، پرداخت اشتباه گسترده
- SEV-2: اختلال عمده ثبت سفارش/ورود یا اثر بر گروه بزرگی از کاربران
- SEV-3: خرابی محدود با workaround
- SEV-4: اشکال ظاهری یا درخواست عادی بدون اثر جدی

برای SEV-1 و SEV-2، Incident Commander واحد، timeline زنده و کانال هماهنگی مشخص لازم است.

## 6. Runbook: API در دسترس نیست

1. health را از داخل و خارج شبکه بررسی کنید.
2. وضعیت Kestrel/systemd/IIS و reverse proxy را ببینید.
3. log همان بازه و آخرین deployment را مقایسه کنید.
4. اتصال دیتابیس، فضای دیسک و permission مسیر داده را کنترل کنید.
5. اگر release اخیر عامل محتمل است، rollback کنترل‌شده انجام دهید.
6. پس از بازیابی login، products و create-order غیرمالی را smoke test کنید.
7. timeline و علت نهایی را ثبت کنید.

## 7. Runbook: سفارش ثبت نمی‌شود

1. status code و message را بدون دریافت token مشتری ثبت کنید.
2. موجودی اقلام و معتبر بودن ProductId را بررسی کنید.
3. انقضای token و ساعت سرور را کنترل کنید.
4. خطای constraint، lock یا فضای دیتابیس را بررسی کنید.
5. از ثبت دستی سفارش مالی بدون فرآیند تأییدشده خودداری کنید.
6. پس از اصلاح، یک سفارش sandbox ثبت و در هر دو داشبورد مشاهده کنید.

## 8. Runbook: اختلاف موجودی

1. فروش محصول متاثر را در صورت خطر oversell موقتاً متوقف کنید.
2. سفارش‌های باز و تراکنش‌های موجودی آینده را تطبیق دهید.
3. از تغییر مستقیم دیتابیس بدون ticket، تأیید و audit پرهیز کنید.
4. اصلاح موجودی باید reason، actor، before و after داشته باشد.
5. علت ریشه‌ای مانند race condition، لغو بدون بازگشت موجودی یا import اشتباه بررسی شود.

نسخه فعلی جدول InventoryTransaction ندارد؛ افزودن آن اولویت production است.

## 9. Runbook: پرداخت آینده نامشخص

1. به نتیجه مرورگر اعتماد نکنید.
2. OrderNumber، Payment authority و مبلغ را در سرویس پرداخت و دیتابیس تطبیق دهید.
3. verify server-to-server را با idempotency اجرا کنید.
4. اگر پرداخت قطعی نیست، Order را Paid نکنید.
5. اگر پول کسر شده ولی ثبت داخلی شکست خورده، مسیر reconciliation و سپس refund/ثبت معتبر اجرا شود.
6. تمام اقدام‌ها audit و به مشتری شناسه پیگیری داده شود.

## 10. Runbook: حساب مدیر مشکوک

1. نشست‌ها و کلیدهای مربوط را revoke/rotate کنید.
2. دسترسی حساب را موقتاً محدود کنید.
3. audit تغییر محصول، سفارش، موجودی و کاربر را حفظ کنید.
4. source IP/device و زمان رخداد را مطابق سیاست حریم خصوصی بررسی کنید.
5. credential جدید و MFA اجباری شود.
6. دامنه تغییر غیرمجاز و نیاز به rollback داده تعیین شود.

## 11. بکاپ و بازیابی

حداقل سیاست پیشنهادی:

- بکاپ روزانه رمزنگاری‌شده
- یک نسخه خارج از host اصلی
- retention روزانه/هفتگی/ماهانه متناسب با مقررات
- هشدار خودکار شکست بکاپ
- تمرین restore حداقل فصلی
- ثبت RPO و RTO تاییدشده

آزمون بازیابی باید شامل این کنترل‌ها باشد:

- بازشدن دیتابیس بدون corruption
- شمارش منطقی Users، Products، Orders و OrderItems
- صحت چند سفارش نمونه و روابط
- اجرای API روی محیط جدا
- ثبت زمان واقعی restore

## 12. درخواست‌های پشتیبانی مشتری

در ticket فقط حداقل اطلاعات لازم را دریافت کنید:

- شماره سفارش
- زمان تقریبی رخداد
- شرح و تصویر بدون token/اطلاعات کارت
- مرورگر و دستگاه در مشکلات UI

هیچ‌گاه رمز، کد یک‌بارمصرف، token یا اطلاعات کامل کارت درخواست نشود. مشاهده یا اصلاح اطلاعات مشتری باید با احراز هویت و audit انجام شود.

## 13. Postmortem

برای SEV-1/2 حداکثر طی چند روز کاری سند بدون سرزنش تهیه شود:

- خلاصه اثر و مدت
- timeline دقیق
- علت مستقیم و عوامل زمینه‌ای
- چه چیزی تشخیص را کند یا سریع کرد
- اقدام‌های اصلاحی با owner و موعد
- تست یا guardrail جلوگیری از تکرار

## 14. چک‌لیست تحویل شیفت/تیم

- رخداد باز و سطح آن
- release جاری و تغییر اخیر
- وضعیت بکاپ آخر
- هشدارهای muteشده و زمان پایان mute
- سفارش/پرداخت نیازمند reconciliation
- اقدام بعدی، مالک و موعد
