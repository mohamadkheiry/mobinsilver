# گزارش پنج چرخه بازبینی، بهبود و QA نسخه v3

## هدف و دامنه

این گزارش نتیجه پنج دور مستقل «ممیزی قابلیت، اصلاح، تست و بازبینی دوباره» برای فروشگاه، داشبورد مشتری، داشبورد مدیر، API و مستندات مبین سیلور است. معیار انتشار این نسخه، موفقیت buildهای Release/Production، عبور تمام سناریوهای Playwright، نبود آسیب‌پذیری شناخته‌شده در وابستگی‌های production و تطبیق انسانی نسخه رندرشده با کانسپت پذیرفته‌شده بوده است.

## چرخه ۱: تکمیل قابلیت‌های عملیاتی

موارد کشف‌شده:

- فرم تنظیمات مدیر نمایشی و بدون persistence بود.
- خبرنامه رابط داشت اما داده‌ای ثبت نمی‌کرد.
- مدیر امکان ویرایش محصول، جستجوی سفارش و دریافت گزارش واقعی نداشت.
- کاربر نمی‌توانست رمز یا سفارش در انتظار خود را مدیریت کند.
- validation چند endpoint برای ورودی مخرب یا ناقص کافی نبود.
- رابط، ادعای پرداخت آنلاین می‌کرد در حالی که درگاه واقعی وجود نداشت.

اصلاحات:

- مدل‌ها و endpointهای `StoreSetting` و `NewsletterSubscription` با schema upgrade سازگار با دیتابیس موجود اضافه شدند.
- تنظیمات نام، راه ارتباطی، اعلان و فعال‌بودن سفارش در پنل مدیر پایدار شد.
- ویرایش محصول، جلوگیری از slug تکراری و جلوگیری از حذف محصول دارای سابقه سفارش اضافه شد.
- تغییر رمز، لغو سفارش در انتظار و بازگردانی موجودی اضافه شد.
- جستجو/فیلتر سفارش، اعلان‌های مدیریتی و خروجی CSV اضافه شدند.
- روش سفارش به عبارت صریح «پرداخت پس از تأیید کارشناس» محدود شد و ادعای درگاه آنلاین حذف شد.

نتیجه کنترل: build اولیه frontend یک ناسازگاری target با `replaceAll` نشان داد؛ پیاده‌سازی به عبارت منظم سازگار تغییر کرد و build دوباره سبز شد.

## چرخه ۲: بازطراحی فروشگاه عمومی

- هدر مذهبی موردنیاز، ناوبری، هیرو، ریل دسته‌ها، کارت محصولات، فروشگاه، جزئیات، سبد، checkout، صفحات اطلاعاتی، ورود و footer بازطراحی شدند.
- پالت سفید واقعی، ذغالی عمیق، سبز زمردی و طلایی کنترل‌شده جایگزین سطوح سنگین و کم‌خوانا شد.
- حالت‌های موجود، کم‌موجود، ناموجود، loading، error و empty کامل شدند.
- محصولات مرتبط، بازخورد افزودن به سبد و newsletter عملیاتی به تجربه خرید افزوده شد.
- متن‌های ارسال و پرداخت با قابلیت واقعی سامانه هم‌راستا شدند.

نتیجه کنترل: build .NET و React موفق و مسیرهای اصلی فروشگاه قابل استفاده بودند.

## چرخه ۳: بازطراحی داشبوردها

- داشبورد Admin و Customer با سلسله‌مراتب دیداری، جدول‌ها، پنل‌ها و حالت‌های واکنش‌گرا بازطراحی شدند.
- پنجره ایجاد/ویرایش محصول، تنظیمات، گزارش و اعلان‌ها در Admin تکمیل شد.
- drawer موبایل، صفحه امنیت و تغییر رمز، جزئیات/لغو سفارش و پیام‌های نتیجه در Customer تکمیل شد.
- نمودار پیشرفت سفارش برای تمام وضعیت‌های واقعی و حالت لغو اصلاح شد.
- جستجوی نمای کلی Admin که قبلاً inert بود به کنترل واقعی تبدیل شد.

نتیجه کنترل: build کامل موفق و دسترسی نقش‌ها در سناریوهای مرورگر تأیید شد.

## چرخه ۴: دسترس‌پذیری، کارایی و پایداری

- تمام صفحه‌های route-level با `React.lazy` و `Suspense` جدا شدند.
- اندازه gzip فایل JavaScript اولیه از حدود `86.5 KB` به `69.4 KB` کاهش یافت.
- نشست ذخیره‌شده هنگام راه‌اندازی با API revalidate می‌شود.
- بستن منو و drawer با Escape، backdrop موبایل، focus قابل مشاهده، labelها، pattern تلفن و نام قابل‌دسترسی کنترل‌ها تکمیل شد.
- عنوان صفحه برای routeهای اصلی تنظیم شد.
- سناریوهای E2E از چهار تست به ده تست افزایش یافت.

در اجرای نخست مجموعه گسترش‌یافته، دو شکست ثبت شد:

1. ثبت‌نام از checkout به‌علت race در state احراز هویت به داشبورد می‌رفت؛ state مقصد پیش از درخواست capture و وضعیت submit محلی شد.
2. locator موبایل «شمش طلا» بین ناوبری و محتوای صفحه مبهم بود؛ locator به ناحیه ناوبری اصلی محدود شد.

پس از اصلاح، تمام سناریوها عبور کردند.

## چرخه ۵: امنیت، وفاداری بصری و رگرسیون نهایی

- محدودسازی brute-force ورود با پنج شکست در پنجره ۱۵ دقیقه و کلید IP + نام کاربری اضافه شد؛ حساب دیگر تحت تأثیر قرار نمی‌گیرد.
- payloadهای null/ناقص برای auth، پروفایل، تنظیمات، محصول، مقاله و سفارش با پاسخ کنترل‌شده رد می‌شوند.
- تعداد قلم‌های تکراری یک محصول پیش از کنترل Stock تجمیع می‌شود.
- شماره سفارش suffix تصادفی شش‌کاراکتری دارد.
- لغو Admin موجودی را بازمی‌گرداند و سفارش لغوشده terminal است.
- مشکل responsive ناشی از override ترتیب CSS در هیرو موبایل و فضای رندرنشده ناشی از `content-visibility` شناسایی و رفع شد.

### تطبیق بصری

کانسپت مرجع: `design/concepts/storefront-redesign-v3.png`

خروجی واقعی: `qa/storefront-v3-desktop.png` و `qa/storefront-v3-mobile.png`

موارد تطبیق‌شده:

1. نوار مذهبی، هدر RTL، لوگو، ترتیب ناوبری و خط فعال.
2. هیروی دوپاره دسکتاپ با تصویر بدون tint رنگی، fade لبه‌ای و CTAهای سبز/خطی.
3. پالت سفید/ذغالی/زمردی/طلایی و تراکم خطوط و حاشیه‌ها.
4. ریل دسته‌ها، شبکه کارت محصول، badge موجودی و ریتم فضای سفید.
5. بخش اعتماد، راهنمای خرید، مجله، خبرنامه و footer چندستونه.
6. stack خوانای هیرو، grid دو ستونه محصولات و نبود overflow افقی در `390×844`.

کانسپت و خروجی واقعی در اندازه بومی `1536×1024` و بدون بازتولید کانسپت مقایسه شدند. تفاوت‌های عمدی محدود به داده واقعی، چهار محصول ویژه موجود و متن‌های پویا از تنظیمات فروشگاه است.

## دروازه کیفیت نهایی

| کنترل | نتیجه |
|---|---|
| `dotnet build -c Release` | موفق؛ ۰ خطا، ۰ هشدار |
| `npm run build` | موفق؛ typecheck و Vite production |
| باندل JS اولیه | `69.42 KB gzip` |
| `npm audit --omit=dev --audit-level=high` | ۰ آسیب‌پذیری |
| `npm run test:e2e` | ۱۰ از ۱۰ موفق |
| موبایل `390×844` | بدون overflow؛ منو و drawer قابل استفاده |
| دسکتاپ `1536×1024` | بازبینی دیداری و تطبیق با کانسپت |

سناریوهای خودکار شامل پوسته فروشگاه، وبلاگ و مقاله، موبایل، مدیریت مقاله، خبرنامه، ثبت‌نام از checkout، ثبت و لغو سفارش، ویرایش محصول، تنظیمات، CSV، validation و throttle ورود هستند.

## مرزهای صریح نسخه

- درگاه پرداخت آنلاین، verify بانکی و webhook هنوز وجود ندارد؛ checkout فقط درخواست سفارش برای تأیید کارشناس ثبت می‌کند.
- قیمت لحظه‌ای فلز، پیامک/ایمیل تراکنشی و حمل‌ونقل بیرونی هنوز یکپارچه نشده‌اند.
- SQLite و limiter حافظه‌ای برای یک instance مناسب‌اند؛ برای چند replica باید دیتابیس production و rate limiter توزیع‌شده استفاده شود.
- MFA، refresh/revoke session، audit log و ماشین transition کامل سفارش در نقشه راه production باقی مانده‌اند.

## نکته ابزار QA

کنترل مرورگر داخل برنامه در این اجرا با خطای محیطی `failed to write kernel assets ... os error 3` قابل راه‌اندازی نبود. طبق مسیر fallback، Playwright پروژه با Microsoft Edge واقعی استفاده شد؛ تمام ده سناریو و screenshotهای native با همان مرورگر اجرا و ثبت شدند.
